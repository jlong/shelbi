## At a glance

| Dimension | Shelbi | Conductor |
| --- | --- | --- |
| Form factor | Native macOS desktop app, terminal UI and attachable sessions | macOS desktop app and iOS companion |
| Platforms | Desktop: Apple silicon, macOS 15+; CLI/TUI: macOS and Linux | Desktop: macOS; mobile: iOS; no Windows or Linux app |
| Workspace model | Named, persistent worktree slots, reused across tasks | Separate workspace and branch per task; multiple agent chats can share one workspace |
| Where work runs | Your local and SSH-reachable machines | Your Mac or managed cloud sandboxes, with Cloud shutting down November 20, 2026 |
| Agents | Claude Code, Codex and configurable CLI runners | Claude Code, Codex, Cursor and OpenCode |
| Orchestration | Configurable orchestrator agent, workflow YAML and optional Zen Mode | Workspace chats, model picker and in-app review/PR actions |
| Review | Review workspace with Approve/Reject; optional checked automation | Diff viewer, line comments, checks and PR actions |
| Source | Open source, MIT | No public app repository found |
| Cost | Free software; agent usage and machines are yours to pay for | Free for existing users during wind-down; model usage billed separately |
| Availability | Install locally and configure your project | New sign-ups and app downloads closed November 4, 2026 |

**Checked November 4, 2026.** Conductor's
[announcement](https://www.conductor.build/announcement) changes the decision:
new users can no longer sign up or download the app. Existing Pro users keep
Pro features free; existing free users cannot upgrade. Cloud becomes read-only
November 13 and shuts down November 20, when cloud data deletion begins.
Local Conductor receives new models and critical bug fixes until early 2027,
when it starts winding down. Existing cloud users should export before
November 20, using **Settings → Account → Export data**, or move a workspace
and its chats with **Transfer to local**.

## Where Shelbi excels

### A reusable workspace pool

Shelbi declares named workspaces in the project YAML. Each handles one task at
a time and keeps its worktree at
`<machine.work_dir>/.shelbi/wt/<workspace-name>`, switching branches between
assignments. You choose the pool size and which machine owns each slot.
That keeps checkout paths and build caches available across tasks.

Conductor organizes independent tasks around separate workspaces and branches.
It also supports several agents sharing the same workspace when they need the
same files and branch. Shelbi's pool is useful when you want a bounded queue
of reusable workers; Conductor's model fits work you create and review one
branch at a time. See [Workspaces](/docs/concepts/workspaces).

### Your machines, through a desktop or terminal client

Shelbi has a native macOS desktop app as well as the TUI. Both use the same
application model and command registry. The desktop app is now the site's
default view, with Orchestrator, Issues, Changelog, workspace terminals and
review controls.

There are two ways to work remotely. Your hub can dispatch tasks to
[workspaces on other machines](/docs/concepts/workspaces#local-vs-remote-workspaces).
Or you can open a whole [remote project](/docs/concepts/remote-sessions) from
**Connect to Remote Session…**. With matching Shelbi versions, the desktop
opens the full native window over one SSH relay channel per host, without port
forwarding. Different versions fall back to the remote TUI in a terminal view.
Password-only SSH hosts work too, with a macOS sign-in dialog.

Remote agents keep running on their host when your viewing connection drops.
The host must stay running. Conductor's managed cloud workspaces and live team
collaboration are subject to the wind-down dates above. Shelbi's remote
execution uses machines you control.

### An orchestration loop you can edit

Shelbi's orchestrator can run on Claude Code or Codex. Its onboarding lets you
choose the harness and default model, then edit its instructions before
launch. Agent settings and task overrides select worker runners and models,
so a workspace can run different providers across assignments.

The orchestrator's prompt lives at
`<config-root>/agents/orchestrator/instructions.md`, with shared context in
`agents/_shared/preamble.md`. The config root is normally
`~/.shelbi/projects/<name>/`, or `<repo>/.shelbi/` in in-repo mode. Workflow
YAML declares statuses, owners, agents and transition actions. You can inspect
the implementation as well as change the policy. See
[Orchestrator](/docs/concepts/orchestrator) and
[Workflows](/docs/guides/getting-started/workflows).

Conductor also exposes configurable repository prompts and actions. Shelbi
adds access to the orchestration code and project-level workflow definitions.

### A board, review step and shipping record

Shelbi can keep its issue board in local files or use
[GitHub Issues](/docs/concepts/github-issues) as the tracker. The **New task**
dialog has Title, Workflow, Status, Priority and Description fields, plus
**Let Orchestrator write this up** to expand a draft into a task with
acceptance criteria. Both clients also have a project
[Changelog](/docs/concepts/changelog) page for shipped work.

In the default flow, a worker writes `.shelbi/shelbi-ready` to hand off its
branch. Finished work reaches Review, where you can load a dedicated review
workspace and **Approve** or **Reject** it. The
[events log](/docs/concepts/events-log) records transitions as text.

With Zen off, the default workflow waits for your approval.
[Zen Mode](/docs/concepts/zen-mode) can promote backlog work and land finished
branches under configured policy. Configured local checks, CI, conflict and
sensitive-path checks form part of that process. Workflow ownership and per-issue settings
control what can be automated. Keep Zen off when you want to initiate those
decisions yourself.

## Where Conductor excels

These strengths remain useful to existing users during its wind-down.

### Code review inside the app

Conductor's [diff viewer](https://www.conductor.build/docs/reference/diff-viewer)
supports unified diffs, filtering by commit and comments attached to changed
lines that can go back to the agent. Its
[Checks tab](https://www.conductor.build/docs/reference/checks) collects git
status, PR details, CI, deployments, GitHub review threads and todos when
available. That is a useful review surface if you want to inspect code and
feed back on individual lines without leaving the app.

Shelbi also has a native Review view, with reviewer, diff, editor and shell
sessions. Conductor's strength here is its integrated code-review interface.

### Session-level agent and model controls

Conductor supports Claude Code, Codex, Cursor and OpenCode. It bundles Claude
Code, Codex and OpenCode; Cursor runs through its API. Each chat selects a
harness and model, and several chats can share a workspace. Models depend on
the account and provider: Claude models through Claude Code, GPT models through
Codex, Composer 2.5 through Cursor, and provider-supplied models through
OpenCode. See [Harnesses](https://www.conductor.build/docs/reference/harnesses)
and [Agent modes](https://www.conductor.build/docs/concepts/agent-modes).

Recent releases added Haiku 5.5 and GPT-6.1 Terra. Plan Mode, Fast Mode,
reasoning controls and checkpoints vary by harness. Shelbi supports runner
and model configuration too, but Conductor puts these choices directly in the
chat interface.

### GitHub and Linear context at workspace creation

Conductor can start a workspace from a branch, PR, GitHub issue or Linear
issue, then guide it through review, PR creation, checks and merge. See
[Your first workspace](https://www.conductor.build/docs/first-workspace).
For an existing user whose work starts in Linear and finishes in GitHub,
that connection remains useful. Shelbi now has a GitHub Issues backend, so
GitHub integration alone is no longer a reason to dismiss it.

### Workspace actions and preview URLs

Conductor's Run button launches saved actions inside a workspace.
`CONDUCTOR_PORT` supplies workspace-specific ports, and configured preview
URLs appear in the terminal panel's Open menu. Spotlight testing can sync a
workspace back to the repository root for projects that must run there. See
[Testing](https://www.conductor.build/docs/concepts/testing) and
[Settings reference](https://www.conductor.build/docs/reference/settings/reference).

### An iPhone companion

Conductor's October releases added iOS access and remote control of local Mac
workspaces. You can read chats, send prompts, select models and stop agents
from your phone. Remote control is experimental and requires Conductor to
remain open on an awake, online Mac. It connects through Conductor's relay;
this is different from Shelbi's SSH access to your own hosts. See
[Remote Control](https://www.conductor.build/docs/reference/remote-control).
The announcement gives no separate long-term commitment for that relay.

## Choose Shelbi if…

- You want an open-source orchestrator you can install and run on your own
  machines.
- You want a native Mac app or terminal client for a queue of persistent
  workspaces, including workers over SSH.
- You want to open a remote project's full desktop interface while its agents
  keep running on the remote host.
- You want editable workflow policy, a dedicated review step and optional Zen
  automation, with either local files or GitHub Issues as the tracker.

## Choose Conductor if…

New users cannot choose it today: sign-ups and app downloads are closed.
For existing users, continuing temporarily may make sense if:

- Its inline code review, model picker or Linear-to-workspace flow is central
  to your current work.
- You want to finish work in the local app while it still receives model
  updates and critical fixes, through early 2027.
- You are transferring cloud workspaces to your Mac and exporting data before
  the November 20 shutdown. Plan around the published wind-down rather than
  adopting Cloud for new long-running work.
