From the Git repository you want Shelbi to manage, install Shelbi and add the
project:

<Tui>

```bash
brew install jlong/shelbi/shelbi
shelbi project add
```

</Tui>
<Desktop>

```bash
brew install jlong/shelbi/shelbi jlong/shelbi/shelbi-desktop
shelbi project add
```

</Desktop>

Shelbi asks four steps, each prompt starting on what it detected, and writes
nothing until you've answered the last one. Every way of adding a project walks
the same steps and creates the same files: `shelbi project add`, first-run
`shelbi`, [`shelbi init`](/docs/cli/init) (add `-y` to accept every default
without prompts), the TUI's **Add project** dialog, and the desktop app's
**Add Project** wizard.

<Tui>

<Callout type="note" title="Plain shelbi opens the launch screen">

On a fresh machine with no hub daemon running, plain `shelbi` opens the
**Welcome to Shelbi** launch screen instead. Its **Add project** button opens
the same four steps as one dialog (Step 1 of 4 through Step 4 of 4), with the
repo path prefilled to the current directory. With a daemon already running,
plain `shelbi` outside a project starts this same setup for the current
directory.

</Callout>

</Tui>
<Desktop>

<Callout type="note" title="The desktop app's Add Project wizard">

The desktop app asks the same four steps in its own wizard: **Add project** on
the **Welcome to Shelbi** window, **+ Add project** in the project switcher
(click the project name at the top of the sidebar), or **File ▸ Add
Project…**. Pick the **Project folder** (Browse, or type a path), then the
**Agent defaults**, then **Where should issues live?**, then **Where should
settings live?**, and **Create Project** writes the config, agents, and
workflows. **Okay** on **You're all set!** opens the project on its
Orchestrator.

</Callout>

</Desktop>

## 1. Folder

The folder defaults to the top of the Git checkout you're in, and the project's
name to the folder's:

```text
Step 1 of 4 · Folder
? Project folder: ~/code/myapp
? Project name: myapp
  Git repository detected. Shelbi will use this folder as your project.
```

Shelbi also reads the folder's default branch (origin's `HEAD`, then the
checked-out branch, then `main`) and its origin remote, and records both in the
project. Credentials embedded in a remote URL are never written.

Two offers can follow, both on by default:

- **Not a Git repository yet.** Shelbi offers to initialize one:

  ```text
  ? ~/code/myapp is not a Git repo. Initialize one here with git init -b main? (Y/n)
  ```

  Decline and setup continues without Git; Shelbi works best in a repository.
- **A teammate's committed settings.** When the folder holds a committed
  `.shelbi/project.yaml` this machine hasn't registered, Shelbi offers to pick
  it up. That registers the project here, using the committed settings, and
  skips the remaining steps. See [Config modes](/docs/concepts/config-modes).

## 2. Agents

Choose the runner and model your project's agents use by default. The installed
runner is preselected (Claude Code when both Claude Code and Codex are), on the
runner's own default model:

```text
Step 2 of 4 · Agents
? Agent runner:
> Claude Code (2.1.0)
  Codex (0.27.0)
? Default model:
> Use runner default
  Opus
  Sonnet
```

The runner becomes the orchestrator's runner, and the shipped agents recommend
it. Both built-in runner declarations stay in the project config, so you can
switch later.

## 3. Issues

Next, Shelbi asks where this project's board should live:

```text
Step 3 of 4 · Issues
Where should this project's issues live?
  GitHub Issues  cards are GitHub issues your team can see and file (requires `gh` logged in)
  File system    private markdown files on this machine (no GitHub needed)
? Issue tracker:
> GitHub Issues
  File system
```

- **GitHub Issues** stores each card as a GitHub issue. It is preselected, with
  the `owner/repo` pre-filled, when your origin remote is a GitHub repo. Shelbi
  preflights first: `gh` must be installed and authenticated, and your account
  must be able to read issues and create labels on the repo (Issues enabled plus
  push access). If the preflight fails, Shelbi explains the fix and lets you
  retry or fall back to File system, so a GitHub config that would not load is
  never written. On success it creates `shelbi:id/*` and `shelbi:status/*` labels
  on first use and stores a small metadata block in each issue's body.
- **File system** keeps the board as private markdown under
  `~/.shelbi/projects/<name>/tasks/`. No GitHub needed. It's preselected when
  the origin isn't on GitHub.

You can move a board between backends later with
[`shelbi issue-store migrate`](/docs/cli/issue#issue-store-migrate). For the full
picture of what the GitHub backend writes onto your repo (the label scheme, the
metadata block, and how assignees gate Zen Mode), see the
[GitHub Issues backend](/docs/concepts/github-issues).

## 4. Settings

Last, choose where the project's settings live: **global** keeps them under
`~/.shelbi/projects/<name>/`, personal to you; **in-repo** commits them at
`<repo>/.shelbi/` to share with your team. Shelbi recommends one and says why:

```text
Step 4 of 4 · Settings
  Recommended: In repo (origin remote + 3 committers)
? Settings location:
  global
> in-repo (recommended)
```

It recommends in-repo when the repository has an origin remote and at least
two committers, and global otherwise.

Shelbi then creates the project: its config (declaring the local `hub`
machine), the default agents, and the shipped `task` and `subtask` workflows.
The **workspace pool starts empty**: the orchestrator provisions it on first
boot, asking how many workspaces and which naming scheme you want and creating
each with `shelbi workspace add`.

## Land on the dashboard

<Tui>

Shelbi prints `✓ Project <name> created.` and launches the TUI. On a
file-system board, the new board contains one Backlog card named
**Welcome to Shelbi** (a GitHub Issues board shows your repo's issues
instead). The first time you set up a project on this machine, the sidebar
also briefly shows:

```text
Ctrl+P palette · type E to edit settings
```

The Welcome card is the first hands-on tour. Promote it from Backlog to Todo
and watch Shelbi dispatch it to an available workspace in the sidebar. Open the
command palette with `Ctrl+P`; type `E` to find project and agent settings.
The card is only a guide and is safe to delete.

To change settings later, use that `Ctrl+P`, then `E` path. You can also edit
the generated project files directly and run `shelbi reload`. See
[Project configuration](/docs/configuration/project) for the full schema and
[Config modes](/docs/concepts/config-modes) if you want to share config through
the repository.

</Tui>
<Desktop>

Shelbi prints `✓ Project <name> created.` and launches the TUI in that
terminal. The desktop app is a second client over the same daemon, so open
**Shelbi.app** and pick the project under **Projects on this Mac**, or from the
project switcher at the top of the sidebar if the app is already open.

On a file-system board, the new board contains one Backlog card named
**Welcome to Shelbi** (a GitHub Issues board shows your repo's issues
instead). The Welcome card is the first hands-on tour: drag it from Backlog to
To Do and watch Shelbi dispatch it to an available workspace in the sidebar.
The card is only a guide and is safe to delete.

To change settings later, open **Settings** (`⌘,`, or the gear at the bottom of
the sidebar): its project section has **Workspaces**, **Workflows**, and
**Agents** pages. The command palette (`⌘K`) also lists **Edit Project
Settings** and the other config files once you type "Edit", and **File ▸ Edit
Configuration** does the same; they open the file in your editor. See
[Project configuration](/docs/configuration/project) for the full schema and
[Config modes](/docs/concepts/config-modes) if you want to share config through
the repository.

</Desktop>

## If something is missing

Press Esc or Ctrl+C at any prompt to leave; nothing has been written yet. If a
place Shelbi writes to is unusable (a file where a directory should be), setup
stops before writing anything, Git initialization included, and names the
path. Without a terminal, or with `shelbi init -y`, a missing runner stops
setup with an install hint:

```text
No supported agent runner was found on PATH. Install and authenticate Claude Code (https://docs.claude.com/en/docs/claude-code) or Codex (npm install -g @openai/codex), then start Shelbi again.
```

## Add another project

Run `shelbi project add` from another repository. It asks the same four steps
and launches the dashboard. You can also use
