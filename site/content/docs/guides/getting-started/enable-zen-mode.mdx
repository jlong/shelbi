By default the orchestrator is the scheduler and you own both ends: you
decide what gets promoted out of backlog, and you accept what comes back
from review. **Zen Mode changes that.** The orchestrator promotes backlog items
it judges safe to run and lands exact-provenance PRs that clear a
project-defined confidence bar.

This page is the practical on-ramp: configure the bar, flip the
switch, and watch one issue land end to end. The
[Zen Mode concept page](/docs/concepts/zen-mode) has the full
reference for everything you can tune.

## Set the confidence bar

Before turning Zen on, tell Shelbi what "safe to merge" means for
this project. The minimum useful config is a list of local checks
the orchestrator runs against every Zen-eligible review before it
lets the PR merge.

<Steps>
<Step title="Add a zen block to the project YAML">

Open the project's shared YAML (`~/.shelbi/projects/<name>.yaml` in
[global mode](/docs/concepts/config-modes) or `<repo>/.shelbi/project.yaml`
in in-repo mode) and add a `zen` block:

```yaml
# ~/.shelbi/projects/<name>.yaml (global mode)
name: myapp
repo: /Users/you/Workspaces/myapp
# … the rest of the wizard's output …

zen:
  checks:
    local:
      - 'cargo test --workspace'
      - 'cargo clippy --workspace --all-targets -- -D warnings'
  ci_timeout: 900   # seconds (15 minutes, the default)
  danger_paths:
    extend:
      - 'crates/shelbi-state/src/migrations/**'
```

Three things to know about that block:

- **`checks.local`**: shell commands run from the worktree root.
  Each must exit `0` for the branch to clear the bar. Anything red
  leaves the issue in `review` for you, with a tagged reason in the
  activity feed.
- **`ci_timeout`**: how long to wait for required GitHub checks to
  settle after the PR opens. Anything still pending when the deadline
  hits bails out. Integer seconds; default `900` (15m). A duration string
  like `15m` is rejected and stops the project YAML from loading.
- **`danger_paths.extend`**: globs the orchestrator treats as too
  sensitive to auto-merge. Shelbi already ships built-in danger
  paths and detects more from your project shape (cargo workspace,
  next.js app, `.github/`, etc.); `extend` adds yours on top.
  `override` replaces everything if you want the explicit list.

</Step>
<Step title="Apply the change">

```bash
shelbi reload
```

</Step>
<Step title="Verify Shelbi sees the config">

```bash
shelbi zen status
```

```

  - cargo test --workspace

  - crates/shelbi-state/src/migrations/**

```

The danger-path list is the fully resolved set of guarded globs: the
built-in defaults, the globs contributed by your detected project shapes
(`detected: …` names them), and anything you added under `extend`,
deduped into one flat list. If something you expected to be guarded
isn't on it, add it under `extend`.

</Step>
</Steps>

## Flip the switch

Any of these works:

- **CLI**: `shelbi zen on`

<Tui>

- **Palette**: `Ctrl+P` → **Turn Zen Mode on**
- **Hotkey**: `Alt+Z` (the `global.zen_toggle` binding) while the Activity
  view has focus

The first time you turn Zen on from the TUI, an **Enable Zen Mode?** intro
explains what it does (tick "Don't show this again" to skip it next time).

**Rebinding**: if your terminal swallows `Alt` (macOS Terminal.app does), set
`defaults.global.zen_toggle` in `~/.shelbi/keys.yaml` to another chord,
such as `ctrl-g`, `ctrl-shift-z`, or `'ctrl-\'` (quoted), or rebind it in
**Settings ▸ Keybindings**. See [`keys.yaml`](/docs/configuration/global#keysyaml).

You'll know it's on by the full-width green **ZEN MODE ON** band along
the bottom edge of the sidebar, under the toolbar. That band is the
at-a-glance "the agent is in lead mode" signal. When Zen is off or
paused, the band is simply absent.

## Watch one issue land end to end

Drop a small, clearly-in-scope issue into the backlog:

```
you: tighten the rate-limit error copy to mention the retry window.
```

With Zen off, the card would sit in `backlog` waiting for you to
promote it. With Zen on, the orchestrator scans backlog when a
workspace frees up, runs the **judgment categories** from your
project's `zenmode.md` against each mechanically-eligible card, and
promotes the ones at least one category applies to. You'll see a Zen
row in the Activity view (<Tui>`Ctrl+P` → Activity</Tui><Desktop>`⌘K` → Activity, or **Go ▸ Activity**</Desktop>):

```
promoted Tighten the rate-limit error copy   backlog → todo
```

The dispatch and run that follow look exactly like the manual loop:
the card moves to `in_progress`, the workspace badge flips to working, and
the agent works the prompt.

<Callout type="warning" title="Zen only auto-merges without a review workspace">

If the project declares any `review`-tagged workspace (new projects do, and
the [review workspaces](/docs/guides/getting-started/review-workspaces) guide
sets one up), Zen still auto-promotes and dispatches, but it never runs the
bar on a handoff: every finished issue waits for you to load it and Approve
on the review slot. Remove the slot (or its `review` tag) to let Zen merge on
its own.

</Callout>

What changes is what happens when the workspace writes its review-ready
marker. Instead of stopping at `review` for your inspection, the
orchestrator runs the bar:

```text
review-marker -> probe (local checks, merge conflict, diff size, danger paths)
              -> orchestrator's own review of the diff vs the issue
              -> pr-create (only if no matching PR is open)
              -> ci-watch
              -> move to done (the review -> done transition merges)
```

The probe, PR, and CI steps are single-purpose CLI primitives (see
[`shelbi zen`](/docs/cli/zen)). The probe's repository, base, reviewed head,
and prebuilt integration commit are passed unchanged to `pr-create` and
`ci-watch`, so CI runs on exactly the candidate that was reviewed, and any
movement fails closed. The `in-progress → review` transition already opened
the PR, so `pr-create` only runs when it's missing or has drifted. The merge
itself belongs to the workflow: moving the card to `done` fires the
`review → done` transition, which pushes and merges the branch. (`shelbi zen
pr-merge` is reserved for the release flow; running it on an ordinary issue
would merge twice.)

```
2026-06-22T14:31:08+00:00 project=myapp task=tighten-rate-limit-error-copy workflow=task review -> done reason=orchestrator:zen-merge_pr=241 from_category=handoff to_category=done
```

The `review → done` move merges the branch, and the card lands in **Done**:

Fail any of them (a flaky test, a too-large diff, a touch on a
danger path, a red CI) and the card stops in `review` for you, with
a tagged reason line that tells you why:

| Reason | Meaning |
| --- | --- |
| `zen:failed-checks cmd=… exit=…` | A `checks.local` command exited non-zero. |
| `zen:diff-too-large files=… lines=…` | Diff exceeded the size threshold. |
| `zen:danger-path paths=…` | One or more danger-path globs matched. |
| `zen:merge-conflict files=…` | Branch wouldn't merge cleanly. |
| `zen:ci-timeout duration=…` | CI didn't settle within `ci_timeout`. |
| `zen:review-reject` | The orchestrator's own diff review failed; the card goes back to `todo` with its findings. |

The card behaves like any other manual review from there. You review
the branch, fix what needs fixing, and either accept it yourself (move
it to `done`) or push new commits that clear the bar on the next attempt.

## The activity feed

Zen-driven moves show up in the **Activity** view (<Tui>`Ctrl+P` → Activity</Tui><Desktop>`⌘K` → Activity, or **Go ▸ Activity**</Desktop>).
Press `z` (or click the **Zen** <Tui>pill</Tui><Desktop>filter</Desktop>) to filter the feed down to them,
so machine-initiated actions are easy to separate from anything you
did. The most common reason strings:

| Reason | When it fires |
| --- | --- |
| `orchestrator:zen-promote category=<n>` | The orchestrator promoted a backlog card under judgment category `<n>`. |
| `orchestrator:zen-decline reason-text=<short>` | A mechanically-eligible card was considered and explicitly left in backlog; the orchestrator surfaces it in its next reply. |
| `orchestrator:zen-merge pr=<n>` | A reviewed issue cleared the bar and landed on `main`. |

`shelbi events tail --follow` shows the same lines in raw form if you
want to watch from a shell. In the raw log, spaces in a reason become
underscores (`orchestrator:zen-promote_category=2`,
`orchestrator:zen-merge_pr=241`).

## Pause and stop

Three flavors of "stop", in increasing severity:

- **`shelbi zen pause`**: softer. No *new* auto-promotions, but
  Zen issues already mid-flight keep applying the bar. Use this when
  you want to triage incoming work yourself for a bit without
  aborting in-flight merges.
- **`shelbi zen off`** (or the Zen toggle in the app): hard off. New
  auto-promotions stop and the orchestrator stops initiating the
  merge bar on review handoffs. Anything already in the bar runs to
  completion on its current trajectory.
- **Per issue**: set `zen: { enabled: false }` in the issue's
  frontmatter to keep Zen from auto-promoting it, without changing the
  global mode. Moving a card back to `backlog` alone doesn't stop Zen
  from re-promoting it later (only your own `todo → backlog` demotion
  does).

### Crash recovery

If the orchestrator's session dies mid-run, Shelbi relaunches it
automatically, and Zen keeps the mode it was in. If you'd rather look
over in-flight work before Zen carries on, run `shelbi zen pause` (or
`shelbi zen off`), check, and turn it back on with `shelbi zen on`.

## Tune the bar over time

The values you set in `project.yaml` are the easy half. The
**judgment categories** that decide *which* backlog items the
orchestrator considers promoting, and the merge conditions it applies,
live in a policy file you own, not the YAML:

```text
~/.shelbi/projects/<name>/zenmode.md      # global mode
<repo>/.shelbi/zenmode.md                 # in-repo mode
```

Open it from the palette (**Edit Zen Mode**) or any editor. Its first
line is the one-line summary the heartbeat re-injects into the
orchestrator, so keep it accurate when you change the policy. You can
tune the auto-promote logic for your project (what counts as
"routine," when to refuse, how to phrase a decline) by editing
prose, not code. The next page,
[customize the orchestrator prompt](/docs/guides/getting-started/custom-workflow),
walks through doing it end-to-end.

In the meantime, the deep reference for everything Zen touches:

- [Zen Mode](/docs/concepts/zen-mode): the full mental model, the
  high-confidence bar, judgment categories, per-issue overrides,
  configuration reference.
- [`shelbi zen`](/docs/cli/zen) - every subcommand the orchestrator
  sequences during exact-provenance auto-merge, callable by hand for one-off
  probes.
- [The events log](/docs/concepts/events-log): the canonical format
