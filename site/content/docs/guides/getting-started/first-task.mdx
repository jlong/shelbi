An issue moves through five columns: **Backlog → Todo → In Progress →
Review → Done**, with a sixth, **Canceled**, for work you drop. You drive the
ends: what lands in the backlog and what
gets accepted out of review. The orchestrator drives the middle: the
moment a card hits todo, it picks a free workspace and starts it.

## Open the TUI

From inside the project's repository:

```bash
shelbi
```

Inside a registered project's `work_dir`, `shelbi` opens that project's TUI
(Shelbi resolves by reverse-lookup against `~/.shelbi/projects/*.yaml`).
Anywhere else, with no hub daemon running, it opens the launch screen: pick
your project under **Projects on this Mac** (↑↓ to move, ⏎ to open).

You can also target a project by name:

```bash
shelbi -p myapp
```

The TUI is two panes. A borderless sidebar on the left lists the project
name, the nav (Orchestrator, Issues, Changelog), your declared workspaces, and
any issues waiting on review. The right pane opens on the Issues board;
**Orchestrator** switches it to the orchestrator's live session.

`Ctrl+P` opens a fuzzy command palette. Use it to switch projects, jump
to a workspace, or swap the right pane to another view, including Activity
and Machines, which live only in the palette. `Enter` on a
sidebar row activates it: focus a workspace, open a review, switch to the
Issues board.

## Add an issue

You have two ways in: through the orchestrator (the easy one) or
directly via the CLI.

### Through the orchestrator

The orchestrator is the conversational front door. Tell it what you
want in plain English:

```
you: fix the login bug on Safari: cookie domain mismatch
     breaks the SSO redirect.

Orchestrator: ✓ added to backlog as `fix-login-bug-on-safari`.
              branch: you/fix-login-bug-on-safari
```

Branches are named `<your GitHub login>/<issue id>`, so `you` stands for your
GitHub login throughout this page.

The orchestrator creates an issue card in the **backlog**
column. It won't auto-promote. The backlog is *your* triage queue.

### Via the CLI

Same end result, no chat:

```bash
shelbi issue add "Fix login bug on Safari"
```

Flags you'll reach for occasionally:

```bash
shelbi issue add "Fix login bug" \
  --id fix-login \
  --status todo \
  --description "Cookie domain mismatch breaks the SSO redirect." \
  --depends-on auth-refactor \
  --prefers-machine devbox
```

- `--id`: override the auto-slug.
- `--status`: drop straight into todo (or any other column).
- `--description`: fill in the issue body now instead of editing later.
- `--depends-on`: record a dependency (repeat for several). The card shows
  🔒 until each dependency is in `done`, its PR targets the parent's branch
  while the parent is open, and merging the parent restacks it. Starting
  it is refused while a parent hasn't started yet (still in Backlog or
  Todo) or was canceled; once the parent is in progress, the card can be
  dispatched and its branch stacks on the parent's.
- `--prefers-machine`: the orchestrator only dispatches the issue to a
  workspace on that machine, leaving it in Todo until one is free.

### Via the kanban view

Press `Ctrl+P` and pick "Issues", or hit `Enter` on the **Issues**
sidebar nav. You land on the Kanban board, one column per status (Backlog,
To Do, In Progress, Review, Done, and Canceled; an empty column folds to a
narrow strip). Keys:

| Key | Action |
|---|---|
| `h` / `l` | Step between columns |
| `j` / `k` | Step between rows in the current column |
| `Enter` / `Space` | Open the highlighted card |
| `H` / `L` (shift) | Move the selected card to the previous / next column |
| `K` / `J` (shift) | Reorder within a column |
| `r` | Refresh |
| `Tab` | Cycle the workflow filter |
| `o` | Open the selected card's workspace |
| `/` | Search cards |
| `f` | Filter by workspace |
| `Esc` / `q` | Close an open card |

Adding an issue from the kanban view goes through the orchestrator, so it's
faster to just talk to it in chat.

## Promote to todo, watch the auto-dispatch

Promotion is the start signal. Move a backlog card into **todo**,
either by hitting `L` (shift-l) on the card in the kanban view or by
asking the orchestrator to:

```
you: promote fix-login-bug-on-safari.

Orchestrator: ✓ moved to todo. dispatched to delta.
                workspace: delta
                branch: you/fix-login-bug-on-safari
```

The orchestrator reacts to the move on the event log
(`~/.shelbi/events.log`). It scans the workspace pool, picks the first
free workspace in YAML declaration order (honoring `prefers_machine` if
set), and runs:

```bash
shelbi issue start fix-login-bug-on-safari --workspace delta
```

That moves the card to **In Progress**, creates the branch
`you/fix-login-bug-on-safari` in the workspace's worktree, and feeds
the issue prompt into the workspace's agent CLI. The sidebar badge next to
`delta` flips from `·` (idle) to `⏵` (working).

Jump in any time. `Enter` on the workspace's sidebar row drops you straight
into its pane to watch the run live.

| Badge | Workspace state |
|---|---|
| `·` | idle: no issue assigned |
| `⏵` | working: agent actively running a turn |
| `?` | awaiting input: finished a turn, sitting at the prompt |
| `⚠` | awaiting permission: showing a permission dialog |
| `⏸` | paused: runner stalled on a usage/session limit |

A finished dev workspace doesn't get its own completion glyph: on promotion
the poller closes its session, so the row reads idle (`·`) immediately. The
"done, awaiting human" state lives in the sidebar's review sections, not on
the workspace row.

## Review the branch

When the workspace finishes, it writes a review-ready marker into its
worktree. The hub poller picks it up on the next tick and moves the card
into **Review**. The `in-progress → review` transition pushes the branch
and opens a PR, the workspace's session closes, and its row drops back to
idle (`·`). The card shows in the sidebar's *Queued for Review* section:

```
Queued for Review
· Fix login bug on Safari
  ⎇ you/fix-login-bug-on-safari
```

Review the change in the PR's diff. To *run* it as well (boot its dev server
and click through the app), tag a workspace for review; see [set up review
workspaces](/docs/guides/getting-started/review-workspaces). With a free
review workspace, the hub daemon loads the queued card onto it automatically
(or press `Enter` on the queued row to pick a slot), and the Review agent
serves the branch there. The row then moves to *Ready for Review* with a `✓`
and its `machine:workspace` location. A fresh project has no review workspace,
so `Enter` on the queued row only reports "No review workspace is
configured." and the card waits in the queue.

## Accept the issue

Accept by moving the card to **Done**: `L` in the kanban view from
**Review**, or:

```bash
shelbi issue move fix-login-bug-on-safari --to done
```

You can also ask the orchestrator in chat:

```
you: merge it.
```

The move runs the workflow's `review → done` transition, which pushes the
branch and merges it. If a PR is open for the branch, Shelbi squash-merges
it through the GitHub CLI (so a PR-protected branch still accepts it);
otherwise the hub squash-merges into the workflow's base branch (`main` in
the shipped `task` workflow) and pushes. Asked to merge, the orchestrator
runs that same merge action and then moves the card to Done itself.

The dev workspace has been free since the handoff, and the orchestrator
dispatches it to the next ready todo card on its own.

<Callout type="note" title="You own the Review → Done move">

The orchestrator never moves an issue out of Review on its own initiative.
Deciding when an issue reaches Done (and with it, the merge) is the human
checkpoint, until you hand that step off to
[Zen Mode](/docs/guides/getting-started/enable-zen-mode).

</Callout>

## What just happened

You added an issue, promoted it, watched a workspace pick it up, reviewed
the result, and merged it. The same loop (backlog → todo → in progress
→ review → done) is the whole product surface. Everything else is
volume: more issues at once, more workspaces, more machines.
