```text
shelbi remote connect <HOST> [PROJECT]
shelbi remote list [--json]
```

## shelbi remote connect

`shelbi remote connect` opens a project of Shelbi on another machine in this
terminal: the same thing **Connect to Remote Session** does in the apps,
without the dialog. `HOST` is an SSH alias or `user@hostname`; `PROJECT` can be
left out when the machine has just one project.

It signs in with your own SSH setup (never a password), checks the other
machine's Shelbi, remembers the session in **Recent remote sessions**, and runs
that machine's Shelbi for the project here. If the connection drops it shows
"Reconnecting to *host*… (attempt N)" and keeps trying; press Esc to stop.
Quitting the remote Shelbi brings you back.

If Shelbi isn't running on the other machine, it asks before starting it
(`--yes` starts it without asking). See
[Remote sessions](/docs/concepts/remote-sessions) for the errors it can report.

## shelbi remote list

`shelbi remote list` prints what another machine's **Connect to Remote
Session** dialog finds here: the user Shelbi runs as, its version, whether the
daemon is running, and every registered project with its folder. It only
reads. It never starts the daemon or changes a project.

A remote client runs `shelbi remote list --json` over SSH; you can run it by
hand to check what a client will see.

```text
$ shelbi remote list
Shelbi 0.42.0 as jlong (daemon running)
  shelbi  ~/Workspaces/shelbi
  web     /srv/web
```

## Flags

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `-y, --yes` | bool | false | `connect`: start Shelbi on the other machine without asking when it isn't running. |
| `--json` | bool | false | `list`: print the listing as JSON: `protocol`, `version`, `user`, `daemon_running`, and `projects` (each with `name`, optional `label`, and `path`). |
| `--root <PATH>` | string | install-time default / `$SHELBI_ROOT` / `~/.shelbi` | Override the Shelbi root directory. |
