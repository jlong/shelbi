```text
shelbi daemon [OPTIONS] [COMMAND]
```

`shelbi daemon` runs the hub-side daemon that listens on `~/.shelbi/hub.sock`
(overridable via `$SHELBI_HUB_SOCK`) for worker messages and appends
`event`-verb payloads to [`~/.shelbi/events.log`](/docs/concepts/events-log).
The same process also listens on `~/.shelbi/control.sock` (overridable via
`$SHELBI_CONTROL_SOCK`) for the board and issue mutations clients send, and for
each open project it runs the workspace poller and the board-index refresh.

The daemon is **started on demand**: the first time you open a project it is
launched if it isn't already running, and it exits shortly after no project is
open (it stays up at least 15 seconds after starting, then checks every 5
seconds).
There is no service to install. If a daemon crashes while no UI is attached, a
session process restarts it. You rarely run any of these subcommands by hand.

## Subcommands

| Subcommand | Description |
| --- | --- |
| `run` | *(default)* Bind the hub socket and accept worker messages in the foreground until killed or until no project is open. |
| `status` | Print a short human-readable status from the single-instance lock and the socket (no supervisor involved). |
| `stop` | Stop the current root's daemon (the pid recorded in its `shelbi.pid`) without starting a new one. Running sessions keep running. |
| `restart` | Stop the running daemon and start a fresh one on the current binary, directly. Picks up a freshly installed binary and is the path the version-mismatch flow uses. |

Running `shelbi daemon` with no subcommand is equivalent to `shelbi daemon run`:
it binds the hub socket and stays in the foreground, ingesting worker messages
until killed or until no project is open. That's the form the on-demand start
launches. You rarely run it by hand except to debug ingestion.

## Stopping the daemon is safe for running agents

Every agent session runs in its own detached process, not inside the daemon. A
`shelbi daemon stop`, a `restart`, a crash, or a `kill` of the daemon leaves
every session running; the next daemon (started on demand by any client, or by
a session while its project is open) finds them on disk and they stay
attachable.

`stop` and `restart` only ever signal the daemon recorded in the **current
root's** `shelbi.pid` (`--root`, `$SHELBI_ROOT`, or `$SHELBI_HOME`). They refuse,
signalling nothing, when that record no longer names the same process (a stale
or recycled pid) or when the hub socket answers as a different pid than the
record (for example a temp `SHELBI_ROOT` with `$SHELBI_HUB_SOCK` still pointing
at the live hub). A refusal exits non-zero with `not stopping the hub daemon:
<reason>` (or `not restarting the hub daemon: <reason>`). A `stop` with nothing
running prints `shelbi daemon: not running under <root>` and succeeds. On
success `stop` prints `✓ stopped the hub daemon (pid N, from <root>/shelbi.pid)`;
`restart` first retires any leftover launchd or systemd unit from older
releases, waits up to 10 seconds for the new daemon, then prints `✓ hub daemon
restarted on the current binary`.

To exercise daemon start/stop code without touching the live hub, use a fresh
temp root and unset the hub sockets:

```bash
env -u SHELBI_HUB_SOCK -u SHELBI_CONTROL_SOCK SHELBI_ROOT="$(mktemp -d /tmp/shb.XXXX)" \
  shelbi daemon stop
```

Never stop a daemon by name pattern (`pkill -f "shelbi daemon"`): every
session and agent on a hub runs the same `shelbi` binary, so a pattern can't
tell the daemon you meant from everything else.

## Flags

Every subcommand accepts the same options:

| Flag | Type | Default | Description |
| --- | --- | --- | --- |
| `--root <PATH>` | string | install-time default / `$SHELBI_ROOT` / `~/.shelbi` | Override the Shelbi root directory. The flag wins over both the env var and the compile-time default. |
| `-p, --project <PROJECT>` | string | env / cwd lookup | Accepted as a global flag but ignored: the daemon is hub-wide and serves every open project. |

## Reverse-forward health and tuning

Every shelbi-routed `ssh` invocation carries a reverse forward so remote workers
can write to the hub's events log over the multiplexed channel. The daemon's
per-project workspace poller rechecks that forward every 120 seconds and repairs
it if it has gone stale.

Two failure modes are transient (direct SSH stays healthy) but can be noisy in the
events log, so the recheck handles them explicitly:

- A flaky `master_open` is retried with exponential backoff before it is
  reported. A blip that self-heals is logged once as
  `detail=master_open_recovered attempts=N status=established`; only an outage
  that survives the whole retry budget logs `status=failed
  detail=master_open_failed attempts=N`.
- Loopback-port exhaustion on a TCP-fallback host is surfaced distinctly as
  `detail=loopback_port_exhausted band=<lo>-<hi> tried=<n>`, so it reads apart from a
  master-open blip. Before allocating, the recheck reclaims the port its own
  prior master was holding, then sweeps the configured band.

These environment variables tune the behavior (all optional; sensible defaults
apply):

| Variable | Default | Description |
| --- | --- | --- |
| `SHELBI_FORWARD_RETRY_ATTEMPTS` | `3` | Master-open attempts before a transient failure is reported. Clamped to `1..=10`. |
| `SHELBI_FORWARD_RETRY_BACKOFF_MS` | `250` | Base backoff between attempts; doubles each retry. Clamped to `<= 5000`. |
| `SHELBI_TCP_FORWARD_PORT_BASE` | `47100` | First loopback port for a TCP-fallback forward. |
| `SHELBI_TCP_FORWARD_PORT_SPAN` | `64` | Width of the loopback band swept on a bind collision. Widen this if you see `loopback_port_exhausted`. |

These are read by the daemon process, which inherits the environment of
whichever client started it. Export them, then run `shelbi daemon restart` from
that shell for them to take effect.

## Examples

Check whether the daemon is running:

```bash
shelbi daemon status
# shelbi daemon: running
#   lock held:  yes
#   listening:  yes
#   version:    0.11.0
#   protocol:   1
#   pid:        64129
#   pid record: 0.11.0
#   open:       myapp
```

With no daemon it prints `shelbi daemon: not running` and `(started on demand
when you open a project)`. Both cases exit `0`. A running daemon with no open
project shows `open:       (no open projects — will exit when idle)`.

Pick up a freshly installed binary (stop the running daemon and start a fresh
one on the current binary):

```bash
shelbi daemon restart
```
