```text
shelbi job run [--label <LABEL>] [--estimate <DURATION>] -- <COMMAND>...
shelbi job watch (--pid <PID> | --ci <SHA> | --pr <NUMBER>) [--label <LABEL>] [--estimate <DURATION>]
shelbi job estimate <ID> <DURATION>
shelbi job list [--all] [--json]
shelbi job log <ID> [-n <N>] [-f]
shelbi job cancel <ID>
```

A job is something the orchestrator (or a worker, see [Jobs a worker starts](#jobs-a-worker-starts)) is waiting on. The hub keeps it in
`~/.shelbi/projects/<project>/awareness.json`, checks it every 5 seconds, and
writes one line to `~/.shelbi/events.log` when it finishes:

```text
<ts> project=<p> job id=j4 kind=command label="desktop tests" status=failed exit=3 detail="<last line>" log=<path>
```

`shelbi orchestrator events next` reports it with kind `job_done`.

A job started with `--estimate` that is still running past it gets an
`overdue` line too (kind `job_overdue`), then another every half the estimate
(at least every 10 minutes) until it finishes. A job with no estimate never
gets one. See [Estimates](#estimates).

```text
<ts> project=<p> job id=j4 overdue estimate=30m elapsed=45m label="desktop tests"
```

| `kind` | `status` |
| --- | --- |
| `command` | `ok` (exit 0) or `failed`, with `exit=<code>` and the last output line as `detail`. |
| `pid` | `exited`. |
| `ci` | `ok` or `failed` (the failing check in `detail`). |
| `pr` | `merged`, `closed`, or `ok` / `failed` once its checks settle. |

## Jobs a worker starts

Any agent can start a job, not just the orchestrator. A `job run` or `job
watch` run inside a workspace's agent session records that workspace (with its
agent and issue), and the job reports back to it instead of to the events log:
when the job finishes, or runs past its estimate, the worker's session gets a
one-line prompt with the label, status, exit code, last output line and the
`shelbi job log` command to read more.

```text
Shelbi job j4 "desktop tests" finished: failed, exit 3. Last line: "test result: FAILED". Read the output: shelbi job log j4 -n 50
```

The prompt goes to the worker only while its session is still up and working
on the same issue. If the session has ended, or the workspace has moved on to
another issue, the job writes its `job` line to the events log as above, and
the orchestrator handles it. `job list` marks a worker's job `by <workspace>`,
`job list --all` adds a `by:` line, and `job log` names who started it.

A worker on a remote machine runs that machine's `shelbi`, whose jobs the hub
doesn't watch, so its result is never routed back. The shipped agent preamble
tells agents to run the command directly where `shelbi` isn't on the PATH.

## run

Runs a command detached and prints its job id at once:

```sh
shelbi job run --label "desktop tests" -- cargo test
```

The command runs in the current directory, with your environment, under your
login shell, in a Shelbi session of its own (`<project>/job/<id>`, never one of
a workspace's). It keeps running after the CLI exits, across a hub daemon
restart and across a quit. It runs in a terminal, so it prints what it would
print in yours, and the Jobs screen shows it live: click a job in the desktop
app, or press Enter on it in the TUI, to open its terminal beside the list
(read-only, with a Cancel button while it runs). Its combined output also goes
to `~/.shelbi/projects/<project>/jobs/<id>/output.log` as plain text (the
event's `log=`), and its exit code and last 20 lines to `result.json` beside
it. Read the output with [`shelbi job log`](#log). The session is removed once
the job ends; a finished job's sheet shows its saved output.

## watch

Watches something already running:

| Option | Meaning |
| --- | --- |
| `--pid <PID>` | A process on this machine, until it exits. |
| `--ci <SHA>` | A commit's CI on GitHub, until every reported check has finished. A short sha or ref is resolved in the current repository. |
| `--pr <NUMBER>` | A pull request, until it merges, closes, or its checks settle. |
| `--label <LABEL>` | A short name for the event and `job list`. |
| `--estimate <DURATION>` | How long it should take. See [Estimates](#estimates). |

CI and PR watches ask GitHub once a minute, and only while the machine is online.

## Estimates

`--estimate` on `job run` or `job watch` takes a duration (`45m`, `2h`,
`1h30m`, as `shelbi issue start --estimate` does): how long the job should
take. Once it has run that long, the hub writes the job's `overdue` line, and
repeats it every half the estimate (at least every 10 minutes) until the job
finishes. A job that hangs is reported, instead of looking the same as a slow
one until its own timeout.

```sh
shelbi job run --label "desktop tests" --estimate 20m -- cargo test
shelbi job estimate j4 45m    # revise it: the total from when the job started
```

`job estimate` revises a running job's estimate. A revision that is already
used up alerts on the hub's next check. `job list` shows a running job's
elapsed time against its estimate (`12m/30m`) and marks one past it
`overdue`; `job log` prints the same on stderr above the output. The history
keeps each job's estimate, so `job list --all` shows how long a finished job
ran against it. The Jobs screen draws a progress bar for each running job with
an estimate, full and in the overdue color once it is past it.

## list

Lists the jobs still being watched, newest first.

| Option | Meaning |
| --- | --- |
| `--all` (or `--history`) | Add the finished jobs after the running ones, newest first, with their status, exit code, duration and log path. |
| `--json` | Print them as JSON. Each job carries a `status`: `running`, or how a finished one ended (`ok`, `failed`, `exited`, `merged`, `closed`, `canceled`), plus `finished_at`, `exit_code`, `detail`, `log`, `estimate` and `duration_secs` when it has them. A running job carries `elapsed_secs`, and `overdue` when it has an estimate. |

### History

A job that finishes, or that you cancel, moves to the project's job history,
`~/.shelbi/projects/<project>/jobs/history.json`, and stays there across hub
restarts. The history keeps the newest 200 finished jobs from the last 30 days,
whichever is fewer. Past that the oldest job is dropped, and its directory (its
`output.log`) with it.

## log

Prints a job's output:

```sh
shelbi job log j4          # the whole log
shelbi job log j4 -n 20    # the last 20 lines
shelbi job log j4 -f       # follow a running job until it exits
```

| Option | Meaning |
| --- | --- |
| `-n, --lines <N>` | Print only the last N lines, like `tail -n`. |
| `-f, --follow` | Keep printing new output until the job exits, then say how it ended. |

It works on a running job and on a finished one while the history keeps its
log. A `pid`, `ci` or `pr` watch has no command output, so `job log` prints the
watch's status instead.

## cancel

Stops watching a job. A `job run` command that is still running is sent
SIGTERM (its whole process group), as is the Cancel button on its sheet. The job moves to the history as `canceled`.
