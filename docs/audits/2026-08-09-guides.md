# Guides audit — docs vs. source / generated CLI help

**Date:** 2026-08-09
**Scope:** all 17 guide pages under `site/content/docs/guides/`
**Method:** audit only, no doc files modified. Every command, flag, config
snippet, event-log line, and TUI depiction in the guides was walked against a
freshly built binary (`shelbi 0.7.2`), the generated `--help` output, and the
current source in `crates/shelbi-cli`, `crates/shelbi-core`,
`crates/shelbi-state`, and `crates/shelbi-tui`.
**Prior audit for dedupe:** `docs/documentation-codebase-audit.md`
(2026-07-13). Everything below was re-verified against current source; the
events-stream and Zen-status findings are new since that pass (events stream
reworked in #521).

Pages covered (all 17): getting-started/{index, install, first-project,
first-task, workflows, custom-workflow, enable-zen-mode, multi-workspace,
review-workspaces}; understanding-workflows/{index, feature-branch, forking,
git-flow, trunk-based}; doing-more-with-agents/{index, add-to-workflow,
adversarial-review-agent}.

Legend: **confirmed-error** = doc contradicts current behavior/source now.
**drift-risk** = doc is loosely worded or relies on deprecated/soon-changing
surface; not wrong enough to break a user today but likely to rot.

## Findings

### F1 — "The category set is closed at **five**" — there are six (HIGH, confirmed-error)

- **Doc:** `getting-started/workflows.mdx:21-23` ("every status maps to a
  small, closed set of **categories**: `backlog`, `ready`, `active`,
  `handoff`, `done`"), `:133-134` ("Every status … declares one of five
  categories"), and `:144-145` ("The category set is **closed at five**. A
  workflow can't introduce a sixth.").
- **Source:** `crates/shelbi-core/src/workflow.rs:1089-1102` — `StatusCategory`
  has **six** variants: `Backlog, Ready, Active, Handoff, Done, Archived`.
  Wire spellings at `workflow.rs:1108-1117` include `"archived"`; `FromStr`
  accepts it at `:1130-1135`.
- **Internal inconsistency:** the sibling guides all *use* the sixth category:
  `understanding-workflows/feature-branch.mdx:106`
  (`{ id: canceled, name: Canceled, category: archived }`),
  `understanding-workflows/git-flow.mdx:110`,
  `understanding-workflows/forking.mdx:105`, and
  `doing-more-with-agents/add-to-workflow.mdx:32-34` explicitly lists the
  vocabulary as six: "`backlog`, `ready`, `active`, `handoff`, `done`,
  `archived`". The shipped `task`/`subtask`/`default` workflows all declare a
  `canceled` status in the `archived` category
  (`workflow.rs:710-717`, `:798-805`, `:902-909`).
- **Fix hint:** workflows.mdx should say six categories and add an `archived`
  row (terminal — closed without shipping) to the category table at
  `workflows.mdx:136-142`.

### F2 — Shipped accept-edge actions are wrong: `[merge, delete_branch]` vs. actual `[push_branch, merge]` (HIGH, confirmed-error)

The guides that reproduce the shipped workflow files show the `review → done`
(and subtask `in-progress → done`) accept edge as `actions: [merge,
delete_branch]`. The shipped workflows run `[push_branch, merge]` — they push
first and **do not** eagerly delete the branch.

- **Doc claims:**
  - `getting-started/workflows.mdx:547` — task.yaml
    `{ from: review, to: done, actions: [merge, delete_branch] }`.
  - `getting-started/workflows.mdx:600` — subtask.yaml
    `{ from: in-progress, to: done, actions: [merge, delete_branch] }`.
  - `understanding-workflows/feature-branch.mdx:136-137` — the shipped default,
    `actions: [merge, delete_branch]  # squash-merge the PR, delete the branch`.
- **Source:**
  - `crates/shelbi-core/src/workflow.rs:818-822` — `task_workflow()` builds
    `review → done` as `[TransitionAction::PushBranch, TransitionAction::Merge]`;
    the comment at `:814-817` is explicit: "No eager `delete_branch` — the
    merged branch is swept separately, so a bad merge stays recoverable."
  - `crates/shelbi-core/src/workflow.rs:919-923` — `subtask_workflow()`
    `in-progress → done` = `[PushBranch, Merge]` (same "No eager
    delete_branch" note at `:917-918`).
  - `crates/shelbi-core/src/workflow.rs:726` — the built-in `default_workflow()`
    ships with **`transitions: None`** (no transitions block at all), so
    feature-branch.mdx's full `transitions:` listing for `default.yaml`
    (`feature-branch.mdx:130-146`) does not match the shipped `default.yaml`
    either.
- **Note:** the *cancel* edges (`[close_pr, delete_branch]`) in those same
  listings are correct (`workflow.rs:823-832`). Only the accept edge differs.
- **Impact:** a reader copying feature-branch.mdx's block gets a workflow that
  deletes the branch on accept and skips the recovery-oriented `push_branch`
  — a behavioral change from the shipped default, not just a cosmetic one.

### F3 — `shelbi zen status` output block is fabricated (HIGH, confirmed-error)

`getting-started/enable-zen-mode.mdx:78-90` depicts `shelbi zen status` output
whose labels and structure do not match the command. The narrative claim at
`:92-93` ("The resolved danger-path list labels every contribution so you can
see which globs came from where") describes a grouping the command never
produces.

- **Doc shows:** `mode: off` / `checks.local:` / `ci_timeout: 15m` /
  `danger_paths (resolved):` with per-source sub-labels
  (`built-in:`, `cargo workspace:`, `github:`, `extend:`) / `in-flight zen
  tasks: 0`.
- **Source (`crates/shelbi-cli/src/commands/zen.rs`, `print_status` +
  `print_danger_paths`):**
  - `:476` prints `zen mode: {state}` — not `mode:`.
  - `:482` prints `checks:` (or the "(none configured …)" line at `:480`) —
    not `checks.local:`.
  - `:487` prints `ci timeout: {…}` — with a **space**, not `ci_timeout:`.
  - `:561-578` `print_danger_paths` prints one header —
    `danger paths (detected: <shape-labels>):` / `danger paths:` /
    `danger paths (project override):` — followed by a **flat** `  - <path>`
    list. There is no per-source grouping and no `(resolved)` label.
  - `:493-496` prints a `last crash: never` line that the doc omits entirely.
  - `:498` prints `in-flight zen tasks: {n}` — the one line the doc gets right.
- **Fix hint:** regenerate the block from real `shelbi zen status` output and
  drop the "labels every contribution" sentence.

### F5 — `✓` is a review-section glyph, not a "workspace badge" (MEDIUM, confirmed-error/drift)

The guides say a finished workspace's *badge* flips to `✓`. Source is explicit
that the workspace row never carries a completion glyph — a finished dev slot
reads Idle (`·`) immediately, and the `✓` lives in the "Ready for Review"
sidebar section.

- **Doc:** `getting-started/first-task.mdx:190`
  (badge table `` `✓` | review-ready — task moved to the review column ``),
  `first-task.mdx:196-197` ("the workspace's badge flips to `✓`");
  `getting-started/multi-workspace.mdx:231` ("The workspace's badge flips from
  `⏵` to `✓`").
- **Source:** `crates/shelbi-tui/src/app.rs:90-95` — the `Idle` doc-comment:
  "A dev workspace that just finished a task reads Idle immediately … there is
  no lingering completion glyph — the review sections own the 'done, awaiting
  human' state, never the workspace row." The `✓` is the Serving/Ready glyph
  in the review section (`app.rs:1095`, `sidebar.rs:1328-1333`). The
  `WorkspaceBadge` enum (`app.rs:78-96`) has no review-ready variant.

### F6 — `shelbi workflow show` prints a table, not "the resolved YAML" (MEDIUM, confirmed-error)

- **Doc:** `getting-started/workflows.mdx:754` — "`shelbi workflow show <name>`

### F7 — Sidebar Zen indicator reads `ZEN MODE ON` (green band), not a `[ ZEN ON ]` pill (MEDIUM, confirmed-error)

- **Doc:** `getting-started/enable-zen-mode.mdx:112-113` ("the **ZEN ON** pill
  anchored to the bottom of the workspaces column") and the ASCII at `:126`
  (`[ ZEN ON ]`).
- **Source:** `crates/shelbi-tui/src/sidebar.rs:546-579` (`render_zen_row`) —
  On state renders the literal label **`ZEN MODE ON`** (`:566`) as a
  full-width green band (`bg Rgb(0,127,0)`), left-aligned, no brackets; anchored
  to the sidebar footer. Off/Paused renders a dim `"{hotkey} Zen mode"` hint
  (`:593`). There is no `[ ZEN ON ]` pill string anywhere.

### F8 — events.log line examples are missing the `project=` / `workflow=` / `*_category=` fields (MEDIUM, drift-risk)

The `shelbi events tail --follow` samples predate the #521 stream rework. Every
line in `events.log` is now hub-global and carries a leading `project=<name>`
scope; task-transition lines also carry `workflow=` and
`from_category=/to_category=`.

- **Doc:** `getting-started/multi-workspace.mdx:210-214`
  (`task=add-csv-export-to-reports backlog -> todo reason=user:cli`,
  `workspace=alpha none -> working`); `getting-started/enable-zen-mode.mdx:173`
  (`task=tighten-rate-limit-error-copy review -> done
  reason=orchestrator:zen-merge sha=abc1234`); `getting-started/workflows.mdx:673`
  (poller appends `task=<id> <from> -> <to> reason=workspace:ready-marker`).
- **Source:** `crates/shelbi-state/src/event_log.rs:1124-1127`
  (`task_event_body`) →
  `project=<p> task=<id> workflow=<name> <from> -> <to> reason=<r>
  from_category=<c> to_category=<c>` (documented at `:979`). Workspace lines:
  `project=<p> workspace=<name> <prev> -> <new> …`
  (`event_log.rs:764`, prev-token default `"none"` at `:722`). The
  `events` module header confirms the hub-global shape
  (`crates/shelbi-cli/src/commands/events.rs:1-7`).
- **Correct as-is:** the `in_progress` (underscore) rendering the guides use is
  right — `Column` Display emits `in_progress` even though the status *id* is
  `in-progress` (asserted at `event_log.rs:3663`).

### F9 — TUI nav / view labels: it's "Chat / Tasks / Activity", not "Chat, Tasks" or "Machines / Review" (MEDIUM, confirmed-error)

- **Doc:** `getting-started/first-task.mdx:34` ("the nav (Chat, Tasks)") and
  `:36-37` ("one of the built-in views (Chat / Tasks / Machines / Review)").
- **Source:** `crates/shelbi-tui/src/lib.rs:515` and `:616` render exactly
  three nav entries: `("💬","Chat"), ("📋","Tasks"), ("⚡","Activity")`. There
  is no "Machines" or "Review" nav/view — the third is **Activity**; the
  sidebar groups workspaces under machine headers but that is the Workspaces
  section, not a "Machines" view.

### F10 — `shelbi reload` respawns the "Activity" pane, not a "Review" pane (LOW, drift-risk)

- **Doc:** `getting-started/install.mdx:180` ("only the sidebar, Tasks, and
  Review views need a manual `shelbi reload`"); `getting-started/custom-workflow.mdx:242`
  ("respawns the sidebar, Tasks, and Review panes against the new config").
- **Source / help:** `shelbi reload --help` lists targets `chat`, `tasks`,
  `activity`, `sidebar`, `workspace <name>`, `all` — and the summary line
  "Respawn the shelbi-owned panes (sidebar + tasks/machines) AND the
  orchestrator pane". There is no "Review" reload target; the third pane is
  `activity`. (Same "Review" mislabel family as F9.)

### F11 — `shelbi task list --column done` uses a hidden, deprecated alias (LOW, drift-risk)

- **Doc:** `getting-started/custom-workflow.mdx:156` — "Track this against the
  `done` column via `shelbi task list --column done`."
- **Source / help:** `shelbi task list --help` — the flag is `--status`;
  `--column` is documented as "accepted as a hidden alias for one release
  while older scripts catch up." It works today but is slated for removal;
  prefer `--status done` (and `--workflow`, which composes).
